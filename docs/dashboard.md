# Dashboard

The fullscreen terminal UI — one view, panes, keys, and the command palette.

[← back to the README](../README.md)

The dashboard runs fullscreen in the terminal's alternate buffer (like vim or htop): it uses your whole window, adapts its layout to the terminal size (a third, wide-mode pane appears at ≥110 columns), and restores your terminal exactly on exit. Run it from a real TTY, not piped or backgrounded:

```bash
junco dashboard
```

Everything lives in **one view**. The left rail is the navigation spine: every repo junco knows about on top — watched GitHub repos _and_ local checkouts discovered on disk — with a pinned **system** group below (Queue, Outbox, Worktrees, Daemon, Logs). The body follows the rail cursor:

- a **watched GitHub repo** shows its trigger-labeled issues (and, on wide terminals, a PR monitor pane) — an interactive terminal UI over the same [GitHub-integrated mode](./github-mode.md);
- a **local-only or unwatched repo** shows a repo detail panel: path, origin, branch@sha, dirty flag, its ticket worktrees, and its recent queue activity;
- a **system row** shows that section's body — the machine-local runtime underneath it all.

With `github.enabled = false` in `config.json` there is simply no GitHub side: watched repos render the repo detail panel too, and no GitHub polling happens — the same single view, minus the issue/PR surfaces.

The header's left side is a breadcrumb trail, dim `▸` joining each step: the active repo alone in the main view (`acme/reef`), `acme/reef ▸ #124` in the issue detail, `acme/reef ▸ PR #86` in the PR detail, `system ▸ queue` (or `outbox`/`worktrees`/`daemon`/`logs`) for a system row's body, `command ▸ <name>` while a palette command's output is open (e.g. `command ▸ junco retry`), `transcript ▸ <ticket-id>` while a ticket's transcript is open, and a full-screen view's own name elsewhere (`pull requests`, `review`).

The right side is a live pulse — chips grouped by a dim `│` into warnings, the 24h/last-task record, what's running right now, and daemon/queue/outbox, in that order. Any chip is hidden individually when it has nothing to say (zero count, no data yet), and an empty group drops its separator too:

| Chip                              | Meaning                                                                                                     | Shown                                        |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `⬆ v0.9.1`                        | a newer junco release is on npm                                                                             | wide, when newer                             |
| `watchlist!`                      | the watchlist file is unreadable                                                                            | any, on error                                |
| `gate ⚠ <reason>`                 | the provider gate has paused or degraded the daemon (rate limit, outage, budget, or an auth/config problem) | any, when not healthy                        |
| `restart pending`                 | a config change is waiting on `junco restart`                                                               | any, when pending                            |
| `bridge ✗N`                       | GitHub bridge sync errors                                                                                   | wide, when > 0                               |
| `●N review`                       | issues awaiting review (plan-ready or approved)                                                             | any, when > 0                                |
| `⚑N PR`                           | junco-authored PRs needing attention — red when any are checks-failing, yellow for changes-requested        | any, when > 0                                |
| `24h ✓12 ✗1 92%`                  | the 24h task-history record: done / failed / success rate                                                   | wide, hidden until a task has finished       |
| `last ✓ 2m` / `last ✗ 2m`         | the most recently finished task's outcome and age                                                           | wide, once a task has finished               |
| `▸ fix-login`                     | the first running ticket's id (`+N` suffix when more are running)                                           | any, while a ticket is running               |
| `eta 8m`                          | estimated time to drain the waiting queue                                                                   | wide, while waiting and an estimate is known |
| `daemon up 2h13m` / `daemon down` | daemon reachability and uptime                                                                              | any                                          |
| `◐N ⏳N`                          | local queue running / waiting counts                                                                        | any, when > 0                                |
| `⇡N unpushed`                     | unpushed GitHub outbox ops                                                                                  | any, when > 0                                |

Below 110 columns the header keeps only the any-width chips (warnings, the running ticket, daemon, queue, unpushed); the update/bridge/24h-record/last-task/eta chips are wide-only — the full record always lives in `junco status`. The ↻ refresh stamp lives in the daemon detail panel, not the header (see below).

## The rail and the GitHub panes

For a watched GitHub repo, the screen has three zones:

- **Rail** (left) — every repo, with a per-state issue-count badge (plan-ready / working / failed) on watched rows and a `(cfg)` marker on entries that came from `config.json` rather than the watchlist; local-only checkouts show their path tail and source tag instead. Below the repos, a titled `── system` divider sets off the pinned system rows, which carry live badges (`▸N` running — with a `⚠` when the provider gate is paused, `⇡N` outbox depth, `⚑N` stale worktrees, `up`/`down` for the daemon). `enter` (or clicking the selected row again) opens the repo detail panel for any repo row. Press `u` to run an audit on the selected repo (or, from the issues pane with an issue selected, scoped to that issue); findings are parked for review, not filed immediately. Press `v` to open the in-dashboard review view — a per-finding checklist you confirm to file, and comment drafts you preview and post or discard (or review from the CLI: `junco audit review` / `junco audit file` and `junco investigate review` / `junco investigate post`).
- **Issues pane** (middle) — the selected repo's trigger-labeled issues, newest-relevant first, each showing a lifecycle glyph and its current state badge (planning / plan-ready / approved / queued / working / done / failed / denied). `enter` opens the full issue — body plus the posted plan comment — as a fullscreen detail overlay, at any terminal width, scrollable with `↑`/`↓` (a scrollbar tracks the offset once it overflows). Press `n` to draft an investigation comment on the selected issue; the draft is parked, not posted.
- **PR monitor pane** (right, wide terminals only at ≥110 columns) — junco-authored pull requests for the _selected repo only_, titled `PRs · <nwo>`. Same attention-first order as the PRs view below, minus the repo column: a lifecycle glyph, `#number`, title, checks (`✗fail ✓pass ◍pending`), the review/lifecycle badge, and age. `enter` opens a fullscreen PR detail overlay, `o` opens the selected PR in your browser, `esc` returns focus to the issues pane. Empty state: "no junco PRs for this repo".

Both lists render as fixed-width tables: a bold header strip on a tinted background labels the columns — `#`, `title`, `state`, `age` for issues; the same plus `repo`/`checks` for the cross-repo PR views — and the state cell is a colored pill sized to the longest label in its table, so columns never shift as the list scrolls or the selection moves. A row's `#number` cell renders in accent instead of dim when the issue or PR was opened by the junco bot account — only meaningful with a bot account configured (`botAccount.enabled`); the login is resolved once per session via `gh api user` under the bot's own isolated auth directory, the same mechanism `doctor` uses.

On wide terminals the third column is always reserved, whatever the rail shows: a watched repo's issues body keeps the PR monitor above; a system row's body gets an **activity card** — a 7-day per-day sparkline with its totals, the 24h record, and (once there's enough history) average duration, tokens, and cost; a local-only repo's body gets a dim `local repo — no linked PRs` note instead. Full-screen views (the detail overlays, the PRs view, review) replace the whole body and don't reserve it — the PRs view's own side preview (below) lands in that same physical column but is a different mechanism: a full-screen view swapping in its own selection-tracking card, not the main view's reserved-slot placeholder.

Press `p` for the **PRs view** — a cross-repo, flat list of junco-authored pull requests (identified by their `<branchPrefix>` head branch) in the issues pane's slot, sorted attention-first: checks-failing and changes-requested surface at the top, then checks-pending/review-pending, then approved, then drafts, then merged/closed. Each row shows a lifecycle glyph, `#number`, title, repo, checks (`✗fail ✓pass ◍pending`), the review/lifecycle badge, and age; `enter` opens a fullscreen PR detail overlay, `o` opens the selected PR in your browser directly, and `esc` or `p` returns to the main view (focus stays on whichever pane you left). The same overlay opens from the PR monitor pane's `enter` — inside it, `o` opens the browser and `esc`/`q` returns focus to wherever you opened it from (the monitor or the PRs view). On wide terminals a side preview pane still tracks the list selection automatically, showing a fuller card built entirely from data already in the row (no extra fetch): checks breakdown, review decision, mergeable status, `branch ← base`, the originating ticket slug recovered from the branch name, `±` diff stats, age, and an `↗ owner/repo#n` line for opening the PR on GitHub.

The bottom two rows are the shortcut bar. The **actions row** (upper) names what is under the cursor — a repo, `issue #46`, `PR #12`, a system section — and lists what you can do to it: the filled **chat** chip first wherever a repo is in context (`c` — the underlined letter in every chip IS its key; an UPPERCASE letter means shift, reserved for the guarded verbs `Unwatch` / `Delete` / `Prune` / `Restart` / `Discard`, which also keep their confirm modals), then the row's verbs, then `│` and the places you can go (queue, review, PRs). A toast paints over this row for four seconds or until your next key. The **navigate row** (lower) is the same in every view — the structural keys as small keycaps, with `? help` and `q` pinned right — and only its labels change to say what `⏎` or `←` do here. Below 110 columns it drops `g G`, `:` and `,` (they still work, and the help modal lists them).

Structural keys are fixed and never derived:

| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `g` / `G`                                   | jump to first / last                                                                                                                                                                                                                                    |

| `,`                                         | config editor                                                                                                                                                                                                                                           |
| `:`                                         | command palette (there is no `c commands` chip any more)                                                                                                                                                                                                |

`c` from an issue or PR opens the repo's chat with `/issue N` (or `/pr N`) already typed into the composer — enter pulls the thread in, esc discards it.

Mouse works throughout: clicking a row focuses its pane and selects that row; clicking the already-selected row opens it — the repo detail panel for rail repo rows, the issue detail for issues, the fullscreen PR overlay for PRs, the log overlay for the logs row, exactly like `enter`. Clicking blank pane space (no row under the cursor) just focuses the pane, leaving the selection where it was. The wheel moves the selection or scrolls, always acting on whatever pane is under the cursor. The issue detail, the PR overlay, and the PRs-view preview card all carry an `↗ owner/repo#n` line — click it (or cmd+click in terminals that support OSC 8 hyperlinks, or press `o`) to open the issue or PR on GitHub. To select terminal text instead of clicking through the dashboard, hold shift while you drag, same as any other full-screen terminal app.

A guarded action (`Delete`, `Prune`, `Restart`, `Discard`) opens a confirm modal with two clickable buttons — `[ esc cancel ]` and a solid `y confirm` pill, danger-toned (red) for destructive actions and accent-toned otherwise. Click either, or use the keys; both are equivalent, and no other input reaches the dashboard while the modal is open.

Every action is an ordinary label mutation made through your own `gh` auth — the same trust model as labeling an issue by hand on GitHub. Dispatch/approve/re-plan don't run anything themselves; they just move labels that the daemon's sweep acts on.

**The command palette** (`:`) runs the junco CLI from inside the dashboard: type to filter, `enter` to run (commands that take arguments — `list`, `retry`, `outbox`, `submit`, `logs`, `service`, `transcript` — get an args field first), and the command's real output appears in a scrollable pane (a scrollbar tracks the offset once it overflows) with its exit code (`r` re-runs, `esc` returns). Under the hood each run spawns the actual `junco` CLI against the dashboard's own config — no reimplementation, no drift, and no shell in the middle. `logs` runs bounded (`-n 200`); `init`, `start`, and `dashboard` are shown greyed-out with the reason they can't run here (use `restart` for the daemon).

Repos added with `w` (and removed with `x`) live in a small JSON watchlist file at `<dataDir>/watchlist.json`, separate from `config.json`. The daemon's bridge sweep re-reads this file every sweep, so watchlist changes take effect without a restart. Where a repo appears in both, the `config.json` `github.repos` entry wins — that's also why config-sourced repos aren't removable from the dashboard.

## The repo detail panel

`enter` on any rail repo row (or selecting a local-only checkout) opens the full local picture of that repo, laid out as aligned key/value rows under titled `── worktrees` / `── recent tickets` dividers: path and source (config / watchlist / external / clone), origin URL, `branch@sha` with a `✎ dirty` flag, any extra local clones of the same repo collapsed into the row, its ticket worktrees (slug, live/stale/backup class, HEAD, age), and its recent queue activity — running, waiting, and finished tickets whose `repo:` targeted this checkout. Scroll with `[`/`]` (a scrollbar tracks the offset once it overflows); `b` opens the repo on GitHub when it has one; `esc` returns.

## The system rows

The bottom of the rail is the machine-local runtime — the same daemon and on-disk state the queue chips and header pulse summarize, one selectable row per section. Selecting a row swaps the body to that section; `→`/`l`/`enter` moves focus into it, `←`/`h`/`esc` returns to the rail.

- **Queue** — running, waiting, and recent tickets under bold header strips (`running`, `waiting`, `recent`), plus the paused banner, a `↻ poll Ns ago` heartbeat on the running strip, and an `⚠ no activity Nm` warning under a running ticket whose progress has gone stale (5 minutes with no update) — a wedged task surfaces before the supervisor's guards would escalate on it. Each running row also carries a time-budget gauge (`▰▰▰▱▱ 23m / 45m budget`, elapsed since it started against the configured task timeout). Waiting positions match the order the daemon will actually claim (priority first, then filename); the waiting strip shows how many are deferred and the oldest wait time, and each row shows its own `queued Nm` age, with a deferred row also showing its retry backoff (`not before HH:MM`). The recent strip lists the last few finished tickets with their real result status and duration alongside how long ago they finished. Below it, an always-on **STATS** section rolls up the durable task-history ledger (`<dataDir>/data/history/` — or `<dataDir>/history/` on a not-yet-migrated legacy tree) and the daemon's live metrics: a 24h line (done/failed counts, success rate, average duration, and an ETA for the waiting queue), a 7-day line with a per-day sparkline, a spend/token line, a guards-and-outbox line (nudges, kills, requeues, outbox depth), and a restart-needed notice when a config change is waiting on `junco restart`. Every STATS line degrades gracefully, and STATS rows are always read-only, never part of the selectable row list. `enter` on a running or recent row opens its transcript (see below). `t` (retry) requeues a failed ticket; `D` deletes a queued one (confirmed); a done ticket is shown but can't be requeued.
- **Outbox** — the GitHub outbox backlog: live and dead ops, with `f` flushing it (see [Offline / flaky network](./github-mode.md#offline--flaky-network)).
- **Worktrees** — every ticket worktree junco knows about: mapped repo, slug, live/stale/backup class, HEAD, and age. `P` prunes a stale or backup worktree (confirmed); a live worktree is shown but never prunable — the daemon owns it.
- **Daemon** — a scrollable stat grid (a scrollbar tracks the offset once it overflows): a `state` row (`up 2h13m` / `down`, with the pid as a hint) and a `refreshed` row (`↻ 32s ago`, or `—` before the first cycle lands) — that's the GitHub-data refresh cycle, not the daemon's own poll, which is why it lives here and not the header. An `── endpoint` divider sets off inference-endpoint reachability (or a colored gate badge and its reason when the provider gate isn't healthy) and the health host:port; an `── activity` divider sets off guard nudge/kill counts, token in/out totals, a `spend` row (today's cost, with a fill gauge against the daily budget when one is configured), the task-status tally, and live per-ticket turn progress. `[`/`]` scroll it; `R` restarts the daemon (confirmed; in-flight tickets soft-abort, committed work salvaged); `f` flushes the outbox.
- **Logs** — a live, always-following tail of the daemon's `worker.log` (last lines, unfiltered) in the compact body; reads the file directly, so it works whether the daemon is up or down. `enter` or a click expands it into a full-screen overlay (a scrollbar tracks the offset once paused past one screenful) with scrollback and three filters: `f` toggles follow (scrolling away pauses it), `l` cycles the level threshold (debug → info → warn → error), `t` cycles focus to one ticket at a time (every ticket seen so far, then back to all), and `/` opens a substring search. `G`/End jumps to the bottom and resumes follow; `[`/`]` (or the arrows) scroll while paused; `esc`/`q` closes back to the dashboard.
- **Transcript** — `enter` on a running or recent queue row (or `t` on an issue, for the ticket junco built from it) opens the ticket's recorded event transcript as a fullscreen view: one header per run (`run 2/4 · audit · <model> · 01:02:47 · stop · 11m07s · in 34.7k out 1.9k`, or the error line for a failed attempt), then each turn's text and its tool calls (`▸ read game.js  → 214 lines`). `j`/`k` (or the arrows) move a cursor over the tool rows and `enter`/space expands that call's full result under it (capped at 400 lines); `[`/`]` scroll row-wise; `t` shows the model's thinking blocks (hidden by default); `g` jumps to the top. A running ticket's transcript is live: the view follows the tail as the agent works (`f` or `G` toggles/resumes follow, scrolling up pauses it) and flips to the final outcome when the run ends — opening a running row before its agent has started shows `waiting for the agent to start…` and fills in by itself. `esc`/`q` returns to the queue with the cursor where it was. The same rendering is available from the CLI as `junco transcript <ticket-id>`.

Rows the daemon itself owns are never actionable: a running queue row can be selected only to open its transcript (retry toasts instead), and a live worktree guards the prune into a safe toast. Pruning a worktree runs under the daemon's own shared worktree lock with an in-lock liveness gate, so it can never race a ticket that just started using that worktree. Every mutating action — requeue, delete, flush, restart, prune — spawns the real `junco` CLI against the dashboard's own config, the same no-reimplementation, no-drift model the command palette uses; the dashboard has no separate implementation of any of it.

## Component primitives

The panels above share a small in-house kit rather than a UI dependency — each piece is a themed leaf component with NO_COLOR-safe degradation built in:

- **Badge** — a state pill: a label on a semantic background, padded so a column of pills lines up.
- **Rule** — a titled divider (`── title ──────`), used for section headers in the daemon and repo detail panels and the rail's system divider.
- **StatRow** — an aligned key/value line (dim label, bold value, optional dim hint) — the daemon and repo detail panels' grids.
- **Gauge** — a `▰▰▰▱▱` fill bar for a bounded value — the queue's running-row time budget and the daemon panel's spend-vs-budget line.
- **Sparkline** — a per-value bar chart (`▁▂▃▄▅▆▇█`) — the activity card's 7-day trend.
- **Scrollbar** — a right-edge track/thumb indicator on any pane whose content can overflow.
- **Button** — a clickable dialog button (a bracketed `[ esc cancel ]` or a solid pill) — the confirm modal.
- **TableHeader** — the bold column-header strip shared by the issues and PR lists.
