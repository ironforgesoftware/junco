# Dashboard

The fullscreen terminal UI — one view, panes, keys, and the command palette.

[← back to the README](../README.md)

The dashboard runs fullscreen in the terminal's alternate buffer (like vim or htop): it uses your whole window, adapts its layout to the terminal size (a third, wide-mode pane appears at ≥110 columns), and restores your terminal exactly on exit. Run it from a real TTY, not piped or backgrounded:

```bash
junco dashboard
```

Everything lives in **one view**. The left rail is the navigation spine: every repo junco knows about on top — watched GitHub repos _and_ local checkouts discovered on disk — with a pinned **system** group below (Queue, Outbox, Worktrees, Daemon, Logs). The body follows the rail cursor:

- a **watched GitHub repo** shows its trigger-labeled issues (and, on wide terminals, a PR monitor pane) — an interactive terminal UI over the same [GitHub-integrated mode](./github-mode.md);
- a **local-only or unwatched repo** shows a repo detail panel: path, origin, branch@sha, dirty flag, its ticket worktrees, and its recent queue activity;
- a **system row** shows that section's body — the machine-local runtime underneath it all.

With `github.enabled = false` in `config.json` there is simply no GitHub side: watched repos render the repo detail panel too, and no GitHub polling happens — the same single view, minus the issue/PR surfaces.

Above the panes, the header's right side is a live pulse of the daemon: issues awaiting review (`●N review`), junco-authored PRs needing attention (`⚑N PR` — checks-failing or changes-requested, red when any are checks-failing, yellow otherwise), the processed record (`✓succeeded ✗failed`), the most recent task's outcome and age (`last ✓/✗ <age>`), cumulative output tokens (`tok <compact>`), daemon up/down with uptime, the local queue (`◐running ⏳waiting`), and unpushed GitHub outbox ops (`⇡N unpushed`) — every chip but daemon status is hidden when its count is zero or the daemon is down. Below 110 columns the header keeps only the essentials (review, PR attention, daemon, queue, unpushed); the full record lives in `junco status`.

## The rail and the GitHub panes

For a watched GitHub repo, the screen has three zones:

- **Rail** (left, pane 1) — every repo, with a per-state issue-count badge (plan-ready / working / failed) on watched rows and a `(cfg)` marker on entries that came from `config.json` rather than the watchlist; local-only checkouts show their path tail and source tag instead. Below the repos, the system rows carry live badges (`▸N` running — with a `⚠` when the provider gate is paused, `⇡N` outbox depth, `⚑N` stale worktrees, `●`/`○` daemon up/down). `enter` (or clicking the selected row again) opens the repo detail panel for any repo row. Press `s` to run a vulnerability assessment on the selected repo (or, from the issues pane with an issue selected, scoped to that issue); findings are parked for review, not filed immediately. Press `v` to open the in-dashboard review view — a per-finding checklist you confirm to file, and comment drafts you preview and post or discard (or review from the CLI: `junco assess review` / `junco assess file` and `junco analyze review` / `junco analyze post`).
- **Issues pane** (middle, pane 2) — the selected repo's trigger-labeled issues, newest-relevant first, each showing a lifecycle glyph and its current state badge (planning / plan-ready / approved / queued / working / done / failed / denied). `enter` opens the full issue — body plus the posted plan comment — as a fullscreen detail overlay, at any terminal width. Press `c` to draft an analysis comment on the selected issue; the draft is parked, not posted.
- **PR monitor pane** (right, pane 3, wide terminals only at ≥110 columns) — junco-authored pull requests for the _selected repo only_, titled `3 PRs · <nwo>`. Same attention-first order as the PRs view below, minus the repo column: a lifecycle glyph, `#number`, title, checks (`✗fail ✓pass ◍pending`), the review/lifecycle badge, and age. `enter` opens a fullscreen PR detail overlay, `o` opens the selected PR in your browser, `esc` returns focus to the issues pane. Empty state: "no junco PRs for this repo".

Press `p` for the **PRs view** — a cross-repo, flat list of junco-authored pull requests (identified by their `<branchPrefix>` head branch) in the pane-2 slot, sorted attention-first: checks-failing and changes-requested surface at the top, then checks-pending/review-pending, then approved, then drafts, then merged/closed. Each row shows a lifecycle glyph, `#number`, title, repo, checks (`✗fail ✓pass ◍pending`), the review/lifecycle badge, and age; `enter` opens a fullscreen PR detail overlay, `o` opens the selected PR in your browser directly, and `esc` or `p` returns to the main view (focus stays on whichever pane you left). The same overlay opens from pane 3's PR monitor (`enter`) — inside it, `o` opens the browser and `esc`/`q` returns focus to wherever you opened it from (pane 3 or the PRs view). On wide terminals a side preview pane still tracks the list selection automatically, showing a fuller card built entirely from data already in the row (no extra fetch): checks breakdown, review decision, mergeable status, `branch ← base`, the originating ticket slug recovered from the branch name, `±` diff stats, age, and an `↗ owner/repo#n` line for opening the PR on GitHub.

Mouse works throughout: clicking a row focuses its pane and selects that row; clicking the already-selected row opens it — the repo detail panel for rail repo rows, the issue detail for issues, the fullscreen PR overlay for PRs, the log overlay for the logs row, exactly like `enter`. Clicking blank pane space (no row under the cursor) just focuses the pane, leaving the selection where it was. The wheel moves the selection or scrolls, always acting on whatever pane is under the cursor. The issue detail, the PR overlay, and the PRs-view preview card all carry an `↗ owner/repo#n` line — click it (or cmd+click in terminals that support OSC 8 hyperlinks, or press `o`) to open the issue or PR on GitHub. To select terminal text instead of clicking through the dashboard, hold shift while you drag, same as any other full-screen terminal app.

Every action is an ordinary label mutation made through your own `gh` auth — the same trust model as labeling an issue by hand on GitHub. Dispatch/approve/re-plan don't run anything themselves; they just move labels that the daemon's sweep acts on.

**The command palette** (`:`) runs the junco CLI from inside the dashboard: type to filter, `enter` to run (commands that take arguments — `list`, `retry`, `outbox`, `submit`, `logs`, `service` — get an args field first), and the command's real output appears in a scrollable pane with its exit code (`r` re-runs, `esc` returns). Under the hood each run spawns the actual `junco` CLI against the dashboard's own config — no reimplementation, no drift, and no shell in the middle. `logs` runs bounded (`-n 200`); `init`, `start`, and `dashboard` are shown greyed-out with the reason they can't run here (use `restart` for the daemon).

Repos added with `w` (and removed with `x`) live in a small JSON watchlist file at `<dataDir>/watchlist.json`, separate from `config.json`. The daemon's bridge sweep re-reads this file every sweep, so watchlist changes take effect without a restart. Where a repo appears in both, the `config.json` `github.repos` entry wins — that's also why config-sourced repos aren't removable from the dashboard.

## The repo detail panel

`enter` on any rail repo row (or selecting a local-only checkout) opens the full local picture of that repo: path and source (config / watchlist / external / clone), origin URL, `branch@sha` with a `✎ dirty` flag, any extra local clones of the same repo collapsed into the row, its ticket worktrees (slug, live/stale/backup class, HEAD, age), and its recent queue activity — running, waiting, and finished tickets whose `repo:` targeted this checkout. Scroll with `[`/`]`; `o` opens the repo on GitHub when it has one; `esc` returns.

## The system rows

The bottom of the rail is the machine-local runtime — the same daemon and on-disk state the queue chips and header pulse summarize, one selectable row per section. Selecting a row swaps the body to that section; `→`/`l`/`enter` moves focus into it, `←`/`h`/`esc` returns to the rail.

- **Queue** — running, waiting, and recent tickets, plus the paused banner, a `↻ poll Ns ago` heartbeat on the RUNNING header, and an `⚠ no activity Nm` warning under a running ticket whose progress has gone stale (5 minutes with no update) — a wedged task surfaces before the supervisor's guards would escalate on it. Waiting positions match the order the daemon will actually claim (priority first, then filename); the WAITING header shows how many are deferred and the oldest wait time, and each row shows its own `queued Nm` age, with a deferred row also showing its retry backoff (`not before HH:MM`). RECENT lists the last few finished tickets with their real result status and duration alongside how long ago they finished. Below RECENT, an always-on **STATS** section rolls up the durable task-history ledger (`<dataDir>/history/`) and the daemon's live metrics: a 24h line (done/failed counts, success rate, average duration, and an ETA for the waiting queue), a 7-day line with a per-day sparkline, a spend/token line, a guards-and-outbox line (nudges, kills, requeues, outbox depth), and a restart-needed notice when a config change is waiting on `junco restart`. Every STATS line degrades gracefully, and STATS rows are always read-only, never part of the selectable row list. `R` requeues a failed ticket; `x` deletes a queued one (confirmed); a done ticket is shown but can't be requeued.
- **Outbox** — the GitHub outbox backlog: live and dead ops, with `f` flushing it (see [Offline / flaky network](./github-mode.md#offline--flaky-network)).
- **Worktrees** — every ticket worktree junco knows about: mapped repo, slug, live/stale/backup class, HEAD, and age. `x` prunes a stale or backup worktree (confirmed); a live worktree is shown but never prunable — the daemon owns it.
- **Daemon** — a scrollable detail panel: pid, uptime, inference endpoint reachability, health host:port, live per-ticket turn progress, token counts, guard nudge/kill counts, and the task-status tally. `[`/`]` scroll it; `X` restarts the daemon (confirmed; in-flight tickets soft-abort, committed work salvaged); `f` flushes the outbox.
- **Logs** — a live, always-following tail of the daemon's `worker.log` (last lines, unfiltered) in the compact body; reads the file directly, so it works whether the daemon is up or down. `enter` or a click expands it into a full-screen overlay with scrollback and three filters: `f` toggles follow (scrolling away pauses it), `l` cycles the level threshold (debug → info → warn → error), `t` cycles focus to one ticket at a time (every ticket seen so far, then back to all), and `/` opens a substring search. `G`/End jumps to the bottom and resumes follow; `[`/`]` (or the arrows) scroll while paused; `esc`/`q` closes back to the dashboard.

Rows the daemon itself owns are never selectable: running/processing queue rows and live worktrees render — so you can see them — but the cursor skips past them (running) or guards the action into a safe toast (live worktrees). Pruning a worktree runs under the daemon's own shared worktree lock with an in-lock liveness gate, so it can never race a ticket that just started using that worktree. Every mutating action — requeue, delete, flush, restart, prune — spawns the real `junco` CLI against the dashboard's own config, the same no-reimplementation, no-drift model the command palette uses; the dashboard has no separate implementation of any of it.
